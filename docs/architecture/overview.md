# Architecture

This is the plan of record. The [status table](#status) says what exists.

## What this repo is

Humagen is the composition. It owns the pieces that only exist once
the parts are put together: the call tree, governance, routing work to people,
and the stores behind them. It does not reimplement what it composes.

| Part | Owns | Repo |
|------|------|------|
| Event union, bus, egress, connectors, durable runtime, definition pinning | Transport and surfaces | fiber, in this repository at `fiber/` (`github.com/urmzd/humagen/fiber/...`) |
| Agent loop, tools, MCP client, RAG, evals, OTel | Runtime | [saige](https://github.com/urmzd/saige) |
| Sandboxed execution nodes, NGAC | Confinement | [playscape](https://github.com/urmzd/playscape) |
| Durable runs and replay | Crash survival | [anchor](https://github.com/urmzd/anchor) |
| Components and helpers for web, Slack and GitHub | Presentation | This repository: `packages/`, `internal/presentation/github` |

## The presentation boundary

The `packages/` UI libraries and `internal/presentation/github` are components and helpers only. They take data in as props and events and emit actions out.

The test for where something goes: if it needs a network call, a database or an
identity, it belongs in the platform or a surface host. The platform owns the wire. It reads fiber's
`event.Envelope` into Humagen's run model and raises Humagen's actions as
events. `internal/wire` is the only place the two meet.

## The event flow

Every event is one `event.Envelope` with a typed body, and `type` is its only
discriminator, such as `message.posted.v1` or `run.completed.v1`
([fiber's design](../../fiber/docs/architecture/events.md)). A run goes:

```text
surface (console, Slack, GitHub, cron)
  -> ingress: a typed event on its channel (message.posted.v1, github.*.v1, cron.tick.v1)
  -> Platform.Invoke: the agent named, or each that joins (pkg/join); limits and policy (pkg/call)
  -> runtime.Accept: the definition pinned (name, version, digest, sub-agents, policy hash)
  -> anchor: fiber.turn.v2 activities; each turn is a turn.Runtime in a playscape sandbox
  -> run.* events on the bus, on the trigger's channel, under the run's tenant
  -> egress: the sink of the channel's scheme (Slack, GitHub); the API's event stream; the journal
```

- **One bus, by channel and type prefix.** A subscription names a tenant,
  channel prefixes and type prefixes. An empty one receives nothing, control
  channels only reach a subscription that names them, and `run.usage` and
  `run.context` only one that names them. The tenant is the principal's.
- **Hops.** Each event carries `hops`; fiber drops one over `DefaultMaxHops`,
  and an agent's own output never wakes it.
- **At least once.** fiber keys a run by the event and its agent, so a
  redelivered trigger joins the run it started. Humagen keeps its own run
  ids (`runtime.AcceptOwn`), and a call key joins its run.
- **The model reads the catalog.** The trigger reaches the model as its
  catalog rendering, byte stable across replay. A sensitive body (human text,
  private host data) reaches the model but not egress logs or webhooks unless
  a subscriber opts in.
- **Who answers.** Humagen picks agents itself, by name or through the
  dynamic router (`pkg/join`). fiber's channel membership and dispatch
  (`fiber/pkg/membership`, `fiber/pkg/dispatch`) are built but not wired in.

## One primitive: the call

An agent is defined by a spec and runs in a sandbox. When one agent needs
another, it makes a call: a new run of the other agent, in its own sandbox,
raised as a tag on the bus and linked to its caller by an edge.

A subagent, a handoff and a delegation are the same call with a different mode.

| Mode | Context passed | Caller after the call | Answer goes to |
|------|----------------|-----------------------|----------------|
| Subagent | Explicit ordered messages | Waits, then resumes | The caller |
| Handoff, low-level API only | Explicit input | No automatic termination; ownership transfer is not exposed as an agent tool | The inherited surface |
| Delegate | Explicit ordered messages | Keeps working | The inbox, later |

### One origin, two lifetimes

Every run belongs to one origin: the run a person, a schedule or a trigger
started. Runs nest under it as deep as the limits allow, and each records its
origin, its caller and how it was called.

| Lifetime | How it is started | If the caller fails or is stopped | When the caller answers first |
|----------|-------------------|-----------------------------------|-------------------------------|
| Attached | `call_agent` in subagent mode | It is stopped, and so is all that is attached to it | The caller is held open until it ends |
| Delegated | `call_agent` in delegate mode, legacy `delegate_task`, or a low-level handoff call | Nothing. It carries on | Nothing. The caller is done |

What a delegated run attaches dies with it, not with whoever delegated to it.
A run stopped this way is `stopped`, not `failed`, and says why.

### Stopping a run

A stop is the runtime's, not the platform's. `POST /api/runs/{id}/stop` and a
Slack stop button both call fiber's `runtime.Stop` with a reason and who
asked. The runtime records the request on the run in the anchor ledger
(`runtime.WithStopLedger`), so a run still in the queue or between attempts
honours it whenever it starts, and publishes it on the bus to the attempt
executing the run, which cancels the model call in flight and any running
tools, and ends the run with `lifecycle.stopped` carrying what the agent had
said. "Stopped" means cut short: the agent loop judges it, and a turn that had
finished its answer before the request took effect ends `completed`.

| State | Status | `stopping` | What it means |
|-------|--------|------------|---------------|
| Asked | unchanged (`accepted`, `running`, `parked`) | `true` | The request is published. The run can start no further calls from this moment. |
| Stopped | `stopped` | absent | The runtime confirmed it. `answer` is the partial answer people saw, `cause` is the reason. |
| Finished first | `completed` or `failed` | absent | The turn ended before the request reached it. It is reported as it ended, never as stopped. |

The route answers 202 with `stopping` while the run has not ended and does not
wait for it. A run that has ended is answered 200 as it is, so asking twice is
safe. The runtime gives a turn `StopGrace` (ten seconds by default) to wrap up
before it cancels it, and the run still ends stopped. A run in the queue stops
before its first model call when a worker picks it up.

After asking, the platform reads the ledger (`runtime.StopRequested`). A run
the ledger holds no request for had already ended there, so it is settled from
the ledger at once and the route answers 200 with how it ended. When the runtime cancels a
delegation because the caller was stopped (`runtime.ErrStopped` as the
context's cause), the run Humagen started for it is asked to stop too.

A run parked on a person is stopped the same way: the runtime resolves its
question as stopped and ends it without calling a model, and its inbox message
settles as stopped, with the cause.

A run that has answered and is only held open by what it attached has no turn
left to interrupt, and was not cut short. What is attached to it is stopped
through the runtime, and once they have ended it completes with its answer.

If the runtime cannot carry a stop (`runtime.ErrStopUnavailable`, a bus that
cannot be subscribed to), the request fails closed: the run is still marked
`stopping`, so it starts nothing more, the route answers 503, and the run ends
as its own events say. It is never reported stopped while it is still working.

A stopped turn is kept in its conversation. The next turn is sent its partial
answer followed by fiber's `StopMarker` line. Who stopped it and why is not
sent to a model. Housekeeping (titles, memory) does not run after a stopped
turn, an eval case that was stopped is a failed case, and a stopped run counts
as `stopped` in the statistics, not as active.

### Detached branches

The child is a durable run of its own, with its own journal, context window and
topic (`agent:<name>:<runID>`). The caller holds a reference and a result, never
the child's work. Each branch compacts alone, and a tree can spread across
nodes.

Humagen exposes one `call_agent` tool for allowed targets. Its input combines
ordered messages, examples and references, with a discriminated return contract.
The harness resolves and freezes inputs, injects the return instruction, and
validates results. See [Agent calls](agent-calls.md) for the contract and lifecycle.

## Governance rides the edge

| Concern | Rule |
|---------|------|
| Cost | A child leases budget from its caller and settles when it completes: the lease is released and what the child spent, priced by the runtime, becomes the caller's. Limits apply to the whole tree: every run counts against its root's project and client. See [Usage and spend](#usage-and-spend). |
| Access | A child gets the intersection of its spec's access and its caller's grant. It is never wider. |
| Consent | Both sides agree to a call. The caller's spec names the callee in its spawn allowlist, and the callee's call policy (`pkg/callpolicy`) admits the caller: `anyone`, only the agents it `listed`, or `none`. The policy also says which admitted calls wait for a person (`never`, `always`, or callers not `trusted` when `unlisted`), who approves them, and how long they wait. A refusal names the side that refused. The `call_agent` tool offers only the agents both sides agree to. |
| Shape | Depth and fan-out are capped. The zero limits allow no calls. |
| Tracking | Root, parent, depth and trace context travel with the tag, so telemetry shows one tree. |
| Stopping | Stopping a run stops everything attached beneath it, through the runtime. What it delegated carries on. |

## Usage and spend

The runtime reports what every model call used (fiber's `usage` family,
v0.10.0 and later): tokens, cost from saige's price catalog in integer micros
of a currency, and the model's context window. Humagen counts it, holds it
against limits, and stops what goes over.

### Counted once

| Source | When | Key | What it adds |
|--------|------|-----|--------------|
| `run.usage.v1` on a run's stream | As each call completes | The runtime's `accounting_id` | The call, to the usage ledger, under the run's place |
| The run's total (`run.completed.v1` or `run.stopped.v1`, else the ledger's output, else `runtime.RecordedUsage` for a failed run) | When the run ends | `run:<id>` | Only what the calls already counted for the run do not cover: a call whose event was missed |

The platform's observer sees every event (a subscription with no kind filter
receives the usage family). A redelivered call, a redelivered terminal event
and a reconciler pass all find their key already counted and add nothing. A
run is counted as the larger, field by field, of the calls seen for it and its
settled total, and both are kept after it settles: a call whose event arrives
after the settlement (the call a stop cut short is reported late, while the
settlement runs from the reconciler or the stop) adds only what goes beyond
the settled total, in either order. Once a run has settled its `spent` no
longer moves, since it has settled into its caller. A run's settled total is
its own calls (`RunUsage.Own`), never the runs it called, which settle their
own: each model call in a tree is counted once, in the run that made it.

Every ledger entry is stamped with the server's clock when it is appended
(the call's own time is kept as `event_at`), and counts in the period its
stamp falls in, whatever order entries arrive in. Counts are kept per scope
and UTC day as entries are applied, so judging a call reads at most 62 days
of totals.

### Roll-up

An attached run (tagged, the caller waits) is rolled up into its caller: once
it has ended and the ledger records it, the Delegator calls
`runtime.ReportChildUsage`, and the caller's `usage.children` and `usage.total`
include it, once. A delegated run (`delegate_task`) is not rolled up: the turn
that handed it over has moved on, so there is no turn to report it to. Its
spend is the same request's work, so it counts against the same budgets: every
run in a tree counts against its root's project and client, its own agent, and
the workspace. The run manifest's `usage.total` sums every run's own calls in
the tree, attached and delegated alike.

### Enforced

| When | What is judged | What happens |
|------|----------------|--------------|
| A run asks to start | Spend and tokens in the period, with runs and concurrency, under one lock | A scope that has reached its spend limit, to the micro-dollar, or its token limit refuses: 402 for spend, 429 for tokens, with the limit, the policy and its version, and `resets_at` |
| A call is counted | Spend and tokens of every scope the run is in (`policy.Exceeded`), each limit raised for this run by what people granted it there this period | At the warning threshold, one budget alert and one inbox message per scope and limit while it is open. At the limit, the run is stopped through `runtime.Stop`, with a reason naming the limit, the scope and the policy version, a `halted` notice, and one alert. Every other run in the scope is stopped at its own next call. Where the policy's action is `approve`, the run is held for a person instead (see [Approving a run at a limit](#approving-a-run-at-a-limit)); a limit that blocks outranks one that approves |
| A run with a lease spends | Its `spent` plus what it has handed to calls still working (`granted`), against its `lease` | Stopped through the runtime once the two reach the lease |
| A called run ends | Its lease and its spend | The caller's `granted` releases the lease and its `spent` gains what the child spent. If the caller has already settled, the spend climbs on to the nearest ancestor still open, or the root |

An agent's own calls (tagging, `delegate_task`) lease from a metered caller
without naming an amount: each is granted half of what the caller has left.
What is left is read from the calls already counted, and the model call that
asked may not be counted yet, so the other half holds room for it; everything
is trued up when the call settles. A caller with nothing left is refused. A
stop at a limit that could not be requested is asked again at the run's next
counted call. Housekeeping runs are never refused or stopped,
and what they spend is still counted.

### Approving a run at a limit

A policy whose `action` is `approve` names what one approval grants:
`max_grant` (micro-USD) with a spend limit, `max_grant_tokens` with a token
limit. A run in flight that reaches that limit is not stopped. The platform
asks the runtime to hold it (`runtime.Hold`, topic `budget`), and the run
parks at its next batch of tool calls, before any of it runs: one model call
after the one that reached the limit, since that call's usage is reported as
it ends. A `held` notice is written to the usage ledger.

The question is a `budget` question: an approval in the inbox (kind
`approval`, part kind `budget` with the scope, limit, usage and grant), on the
run and in Slack, from Limits. Anyone who reads the run sees it; only
`billing:write` is offered its actions or may answer it.

| Answer | What happens |
|---|---|
| Grant (`approve`) | The run may use the policy's grant more in that scope, in the policy's period. The amount is read from the policy when the grant is made, never more than the question offered; a policy no longer `approve` grants nothing and the answer is refused. The grant is a `granted` entry in the usage ledger with the run, scope, limit, policy version and who granted it, and the run carries on. Reaching the limit plus what was granted holds it again |
| Stop (`deny`) | The run is stopped, with the note as its cause, and the batch it held never runs |
| Nobody answers in time | The same as stop: a hold defaults to a denial |

A run is held once per scope, limit and grant. A hold the runtime cannot
record stops the run as before, so a limit is never left unenforced. A run
asking to start at an `approve` limit is refused as at a `block` one: there is
no run yet to hold. Grants are read from this process's usage ledger (written
to the store and replayed at start), not from the shared counters.

### Unpriced calls and other currencies

A limit is in US dollars. A call saige could not price (a model with no rate
card) and money in any other currency are never counted as zero dollars and
never compared with a dollar limit. They are counted apart: `unpriced_calls`
and `other_costs` on the run, on `GET /api/usage`, and in Analytics, where the
spend is shown as a lower bound. The first such call in a scope with a spend
limit raises one alert, open until settled, saying its spend is a lower bound.
Tokens are counted for every call, priced or not, so `max_tokens` on a policy
is the bound that holds whatever the price.

### Where it shows

| Surface | What |
|---------|------|
| `GET /api/runs/{id}` | `usage` (own, children, total, context), `spent`, `granted` |
| The event stream and `listRunEvents` | `run.usage.v1` and `run.usage.child.v1` |
| `GET /api/usage` | `spend` (used, limit, `unpriced_calls`, `other_costs`) and `tokens` per scope |
| `GET /api/analytics` | `usage` per group: calls, tokens, spend, unpriced calls |
| Console | The run's Activity page (calls, tokens, cost, context), the session gauge's context edge, Analytics, Limits |
| Slack app | Nothing. Usage is not shown on a turn in the console either, so the shared adapter carries none (see [clients](../reference/clients.md#usage-on-a-turn)) |

## People in the loop

A run that needs a person parks on a question. fiber (v0.11.0) owns the
waiting: the question is recorded on the run in the ledger, the run holds no
worker while it waits, and the first answer recorded is the answer. Humagen
owns who is asked and where.

| Question | Raised by | Answered with |
|---|---|---|
| Budget | The platform, when a run reaches a limit whose policy asks for approval (`runtime.Hold`, see [Approving a run at a limit](#approving-a-run-at-a-limit)) | `approve`, which grants the policy's amount and resumes the run, or `deny`, which stops it. Answered by `billing:write` only |
| Approval | A call to a tool the agent's spec lists in `approvals` | `approve` (optionally with edited `arguments`, checked against the tool's schema, and for a call that acts as a person, `tool.acts_for_person` on the run and in the inbox, only by that person, so every approval card says so and none offers an edit of it) or `deny` (with a note the model is shown). In a run whose answers may reach a person's own credentials, only that person edits any of its calls or adds a note, and the question names them (`steered_for`), so an agent's approval queue offers nobody else a note |
| Choice | The agent calls `ask_person` with `options` | `choose` one option |
| Reply | The agent calls `ask_person` without options | `reply` in words |

### Who is asked

Who may answer is decided from the run's pinned revision, so revising an agent
does not change who may answer a question a run already asked:

| Question | Who may answer |
|---|---|
| Approval | `approvers` when the spec names them, else anyone in the workspace. Never the person whose request raised the run, nor the person who started the tree it is in, by any name they go by (a Slack user is also every principal a Slack client of the run's team maps them to, pinned when the run starts), unless the spec sets `self_approval`. fiber's `AnswerRequest` takes no requester alias, so Humagen checks this before it asks the runtime. A GitHub actor is mapped to no principal, so self-approval there is not detected |
| Choice, reply | `answerers` when the spec names them, else anyone in the workspace. A run whose answer may reach the credentials of the person it acts for (it, or a run that called it, acts for a person and is answered by a revision granted a person-scoped tool provider) is answered by that person alone, since an answer steers what its tools, and its callers', are asked next: the question is addressed to them, and anyone else's answer is refused (`maySteer`, `steeredFor`). When `answerers`, a called agent's own for what it asks, leaves that person out, nobody may answer: the run waits until the question expires and takes its default, or until it is stopped |

`approvers` and `answerers` name principals by subject and this workspace's
roles as `role:<name>`. The runtime asks Humagen for a person's roles
(`runtime.WithRoles`): the roles they signed in with, or for a person a surface
answers for, what the authorization policy grants their subject. Anyone else
holds no role, so a role admits nobody it was not asked about.

Each question becomes one inbox message (kind `approval` or `clarification`,
with an `approval`, `choice` or `reply` part), addressed to exactly those
people: a reader sees it only when the spec names them or a role they hold,
and the requester never sees an approval of their own call. The agent's
`asked_of` hint narrows that to whom it asked, when that is one of them; it
admits nobody. A question whose rules cannot be read is addressed to nobody.
Answering needs `runs:write` as well (for a person a surface answers for,
their own grant must include it, not only the surface's credential's), and the
runtime checks who may answer again before it records anything.

Addressing routes a question to its inbox; it is not confidential. The
question and an approval's arguments are also on the run, its event stream
and its manifest, for anyone with `runs:read`. See
[security](security.md#the-inbox).

### Answering

From the inbox (`resolveInboxPart`), on the run (`answerQuestion`), or in Slack,
an answer is one call: `runtime.Answer`, with the person as `By` and the
credential's own subject as `Via`. A refusal is 403 and changes nothing. A
second answer, or one after the question expired or its run was stopped, is
answered with the message showing what was recorded. The decision is recorded
in the inbox's record of changes, with who answered and, for a surface, which
surface user.

The message settles in place when the run resumes (`approved by olu`,
`chose eu-west`), when nobody answered in time (`expired`, with the default
the run carried on with: a denial for an approval), when the run is stopped
while it waits (`stopped`, with the cause), and when the run ends without an
answer (`closed`). A run is woken through the queue as soon as it is answered
or stopped (`runtime.WithWaker`), and at its question's deadline, so a default
applies when it is due. Questions wait a day by default (`QuestionTTL`).

### Called runs

An attached run (tagged) that parks shows its question on its caller's stream
as `lifecycle.child.parked` (`runtime.WatchChildQuestions`), and its message is
addressed by the called agent's own spec. The caller keeps waiting in the
Delegator, holding its place, while the called run holds none. fiber's
`WithChildRuns`, which frees the caller too, is not used: it starts the child
inside the runtime, so the call would bypass Humagen's call path (the spawn
allowlist, depth and fan-out, the lease, admission and spend, the call tree,
and the conversation and sandbox the child shares), and it has no hook for a
host to make or refuse that call. Usage is rolled up as before, by the
Delegator's `ReportChildUsage`, once per child. Since one place is always kept
for work that waits on nobody, parents waiting on parked children can refuse
new attached calls (`ErrBusy`), never hang.

### Calls held for a person

A call the callee's policy holds for a person is decided by `callApproval` in
`internal/platform/call_policy.go`. The `call_agent` tool is an
`native.Approving` tool (`fiber/pkg/turn/native`) built on it, and fiber's
host call tool wrapper forwards `Approving`, so the runtime parks the caller on
an approval addressed to the policy's approvers (`role:manager` and
`role:admin` when it names nobody, so a held call is never open to the whole
workspace). The call goes through only when a person approved that very tool
call; otherwise the callee refuses it. The question waits the policy's
`expires_seconds` (`ApprovalRequest.ExpiresIn`, capped by the runtime), then
is denied.

## Decentralized

A peer node is a connector. One node addresses an agent on another the same way
it addresses a Slack thread, so a cross-node call is a tag with a route.

This depends on execution nodes that publish to the bus themselves. Today
fiber streams out of the sandbox through an in-process channel, so every
agent runs inside the serving process.

## Storage

Target the Postgres wire protocol. AlloyDB is one deployment of it, not a
requirement.

Every store has one choice, memory or Postgres, made in one place:
`platform.Config.Backends`, which `humagen serve -state=postgres` fills from
`HUMAGEN_POSTGRES_URL` through `platform.OpenPostgres`. Agent definitions are
kept by `pkg/agents` on `pkg/state`, and fiber's `pkg/durable` keeps anchor's
run ledger and queue. Humagen's own stores do not each get a SQL
copy of their rules. They keep their logic and indexes in memory, as the read
model, and write the records that state is built from through `pkg/state`: a
namespaced, tenant-scoped document store with a Memory and a Postgres backend,
one table, held to one conformance suite. A store loads its namespace when it
is built, and writes before it reports a change, undoing the change when the
write fails. Three stores fold in events that already happened (the journal,
the run index after a run is recorded, and the usage ledger after an
admission) and write those behind, every 250ms and when the platform stops.

Memory is files. `pkg/drive` keeps versioned file trees, one per person, per
project and per agent, with each version's manifest (path, content hash,
size) and the trees' heads and open proposals on `pkg/state`, and the content
once per tenant, by hash, in the configured blob store. A deployment whose
blob store is in memory keeps memory's content beside its manifests instead,
so a restart that keeps a note's place keeps its text. Versions and content
are read when asked for and held in a bounded cache. `pkg/memory` is the
notes' view of those trees: a note is the file `notes/<id>.md`, approved at
the head and pending as a proposal. The notes kept in its old namespace move
into files once, at start ([RFC 0004](../rfcs/0004-isolated-runs-and-person-context.md#memory)).

Because a store trusts its memory after it loads, this is one writer per
database. `pkg/state` holds a Postgres advisory lock for as long as it is
open, per schema, so a second process is refused at start rather than allowed
to diverge.

`pkg/state` also reads and writes per request, which is how a store stops
needing that lock (RFC 0004, horizontal data). `Lookup` reads one record with
its version, `List` reads one page of one tenant's keys by prefix, at most
`state.MaxList` (1,000) records, with a cursor, and an op may name the version
it read (`state.PutAt`, `state.DeleteAt`) or require no record
(`state.Create`): a write whose record moved fails whole with
`state.ErrConflict`, and the store reads again and retries. Every record's
version is 1 when it is written and one more on every write after; rows from
before versions read as 1. The rules for a store built this way:

- **The tenant is the shard key.** A request reads one tenant, never a scan
  across tenants. Only `Load`, at start, reads a whole namespace.
- **A key starts with what a request pages by**, so a page is a prefix: a
  conversation's messages under `m:<conversation>:`, ordered by `state.Seq`.
- **A write changes one tenant.** A link to another tenant's record is its id,
  and work across tenants is a run that retries, not one transaction.
- **The database is the truth.** A cache in front of it may be dropped at any
  time without changing an answer.

A store built this way opens on `state.OpenPostgresShared`, which migrates the
table and takes no lock, so any number of processes may open it;
`platform.OpenPostgres` hands it to them as `Backends.Shared`, beside the
locked store the rest still need. Converted so far: **feedback**
(`pkg/feedback`), keyed by run (`r:<run>:<seq>`, `x:<run>:<person>`,
`h:<run>`), whose records an older release kept one per key are moved once,
by whichever process opens it first.

The usage ledger's counts are the exception: on Postgres they are kept in the
database, not in memory (`usage.Counters`, tables `humagen_usage_*`). Every
change to the counts is one transaction that moves them and writes the ledger
entry that moved them (`state.WriteTx`), with the entry's key from a database
sequence. A call's spend is counted once by its key whichever process saw it,
under the tenant's advisory lock, since it reads and rewrites its run's row.

The counts an admission moves, runs started and runs in flight, are striped:
`usage.Stripes` (8) rows per scope (`humagen_usage_admits`,
`humagen_usage_slots`, locked through `humagen_usage_stripes`). A policy's run
and concurrency limits are quotas (`usage.Quota`) that `usage.Ledger.Admit`
takes in the transaction that counts the run. A limit is split into a share per
stripe; an admission locks one stripe at random in each scope it has a quota in
and goes ahead when that stripe has room, counting every other stripe at its
share or its count, whichever is more, since no other stripe can pass that
while this one is held. When it has no room, the admission locks every stripe
of those scopes, in order, and goes ahead on any stripe if the total has room.
So the limit is exact, an admission is refused only when the total has reached
it, and admissions far from a limit do not wait on each other; one with no
quota takes no lock. The judge decides the rest (spend, tokens, a lease's size)
and warns, on the counts as they are. Counts a release before stripes wrote
are read as stripe 0. The first start on a database fills the counters from the
ledger's entries. On memory the counts stay in the process.

The event bus is on the same database: fiber's `bus.Postgres` keeps events in
`fiber_events` (with `fiber_event_runs` and `fiber_event_tenants`) and wakes
readers with LISTEN/NOTIFY on one connection per process, whose payload is the
tenant published to, so only that tenant's readers query. It is the default
whenever the stores are on Postgres, and there is no Redis bus. Each tenant's
events have a position of their own (`tseq`), taken under an advisory lock per
tenant, so publishes to one tenant are serialized and publishes to different
tenants do not wait on each other. Egress, the observer and fiber's dispatch
read through consumer groups (RFC 0006): a cursor and a lease per group and
tenant in `fiber_consumers`, so one replica at a time handles a tenant's
events for each, another takes over when its lease expires (15 seconds by
default), and it resumes from the last cursor committed. anchor's Postgres
queue still has no delta log; the bus carries every event, so streaming does
not need it.

A worker stopping mid-claim on Postgres no longer leases a run to nobody:
since anchor v0.5.1 the queue waits out a claim it has already sent, for up
to 5 seconds after the stop, and the worker hands back unexecuted a run a
claim returns after it stopped. Before, the database could carry out a claim
the worker had given up on, and the next process could not resume that run
until its lease ran out, 30 seconds later.

## Limits at scale

Admission and spend are counted in the shared store on Postgres (see [Storage](#storage)): two processes on one database cannot both admit the last run a limit allows, and each sees the other's spend at its next read. Admission is striped, so it no longer waits on one lock per tenant: 32 racers admitting into one tenant from two processes went from about 350 to about 3,500 admissions a second with no limit, and from about 310 to about 2,000 under a run limit (Postgres 17 in Docker on a laptop; `BenchmarkSharedAdmission`). Spend is still counted under one lock per tenant. The rest of the platform is still one process per database, so one replica is still the rule.

### Library and personal settings

The library implementation adds private human-owned memory, fact/decision/preference/person/risk kinds,
expiry excluded from every context layer, provenance and persisted use counts. A preview does not
count as use. Personal forgetting records an attempt before removing the note and does not retain
the forgotten text in its audit snapshot. Personal briefing, notification delivery policy, quiet
hours and privacy choices survive restart; native console notifications now use a bounded durable authenticated delivery worker with immediate, hourly digest, quiet-hour and Off policies. Email is available only when the operator configures delivery and a permitted recipient, and the person opts in. See [native notifications](native-notifications.md) and [email notifications](../guides/email-notifications.md). Audit, Memory and Personal Preferences are mounted under their canonical routes.
The managed Library and shared web foundation are described in
[managed-library.md](managed-library.md).


Memory corrections preserve original provenance and record the editor and review. New note IDs are
opaque, so public IDs do not expose private note volume. Explicit promotion copies a selected
approved, unexpired note to a destination project as a pending suggestion. Only text, kind and
expiry cross the boundary; the copier replaces private source provenance. The destination owners
must review it before it enters context. ReadContext Ask and Never, including forced-approval dry
runs, withhold automatic memory grounding; fixed instructions and briefing preferences remain.
