Humagen Agent Sessions

Agents that work wherever you already are. Every conversation is a session with one agent; agents call agents through their sessions; people join when an agent needs them. Humagen becomes the place that runs and remembers those sessions, not a new chat platform to maintain.

1. Sessions

A session is one agent's conversation. It starts where you are (a Slack thread, a GitHub pull request, the console) and answers there. When an agent needs another agent it opens a child session; when it needs a person it mentions them. Nothing copies Slack: no rooms, no channels, no project chat.

One rule for every session

A session is identified by (parent, agent, label). The parent is either a place (a Slack thread, a PR, a new console chat) or another session. The label is optional.

Situation | Example | Result | 

A person mentions an agent somewhere | @reviewer on PR #5 | The reviewer's session for PR #5 | 

An agent calls another agent | The reviewer calls @security-reviewer | A child session under the review | 

Same parent and agent again | The reviewer asks security a follow-up | Continues that child; it remembers its earlier findings | 

Same parent and agent, with a label | Three security passes at once | security-reviewer#a, #b, #c, each with its own context | 

Explicitly fresh | fresh: true, or "Start fresh" in the @ menu | A new session with a generated label | 

An example

PR #5 in urmzd/orchagentthe place

reviewersessionstarted by a review request; posts the PR review

architect-reviewer#a, #bchildrentwo independent passes, compared by the reviewer

qa-reviewerchildran the tests; its output is evidence in the review

@sampersonasked whether the API change is intended; joined from a Slack DM and asked "catch me up"

People

@person in a session invites them. They are told where they are (Slack DM, email, console) with a link that opens the session.

On joining they can ask for a summary since they last looked, answer the agent's question, or take over the conversation.

A question for a person parks the agent's run without holding a worker, as ask_person does today.

Projects

Without rooms, a project is only a bundle of context: its repos, its connections, its default agents and who may use them. Sessions are filed under a project; there is no project chat, inbox, history or channel. Each person has a Personal project, which replaces "No project".

2. Session tools

Agents get five tools for working with other sessions. People get the same five verbs in the console and the API, with the same permissions, so asking in words and clicking can never disagree.

Tool | Does | API | In the console | 

session_call | Start or continue a child session: agent, brief, optional label, fresh, and wait to block for the answer | POST /sessions with parent | @agent in the composer | 

session_listen | Wait for new messages or the end of one or more sessions. Fan out three calls, then listen for all three | GET /sessions/{id}/stream | The child rows update live | 

session_read | Read up: the transcript, or a summary since a cursor | GET /sessions/{id}?since=&summary=true | "Catch me up" | 

session_status | Track children: who is working, waiting, done or failed | GET /sessions?parent={id} | The session's tree | 

session_link | Cross-reference another session as context or evidence; reading one links it automatically | POST /sessions/{id}/links | Linked sessions in Details | 

Rules

Default deny. An agent calls only the agents its call policy names, reads only sessions in its own tree or ones shared with it, and stops at a depth limit.

Listening is durable. A parent waiting on children parks its run and frees its worker, and resumes when they finish, through durable's signals. Three subagents in parallel cost no idle workers.

Spend rolls up. Children spend from the parent's budget, and the parent's usage includes theirs, as run.completed already does for delegations.

No loops. The existing hop limit and "an agent's own output never wakes it" still apply.

Provenance. A child's message can be cited as evidence, so a review finding can point to the qa-reviewer's test run.

4. orchagent

5. Surfaces and structured answers

One session, rendered natively by each place it reaches. A structured answer such as a review is data the platform checks, then each surface draws in its own form.

Surface | While working | When done | Feedback | 

Slack | Streams in the thread, children as status lines | A card: title, counts, summary, errors first, Open Pull Request, Open Session | Reactions, or the card's thumbs and a modal with reasons | 

GitHub | One status comment, edited | A real review: verdict, body, a line comment per finding with a committable suggestion, evidence collapsed | Committing a suggestion, resolving a finding, reactions, /feedback | 

Console | Steps and child sessions stream | The card; each finding opens the diff at its line; each evidence item opens its step or child session | Thumbs that save on click, and a modal with reasons | 

Review v2

Adds to today's v1: title, verdict (approve, comment, request changes), scope.commit, and per finding location, change (becomes a suggestion), and evidence naming the step or child session that observed it. Counts and emoji are derived from findings. Locations must fall in the diff and changes must apply, or they degrade to the review body; evidence without a step shows as unverified. Agents may Approve only where a project's policy allows it.

5b. Talks like a person

In Slack and GitHub an agent should behave like a teammate who uses those tools well: react instead of announcing, reply in the thread, link instead of quoting, and say only what helps.

Reactions both ways

Who | Does | Means | 

Agent | Reacts 👀 to the message it picked up | Got it, working. Replaces "Working on it" messages | 

Agent | Swaps 👀 for ✅, or ❌ with a one-line reply saying why | Done, or could not | 

Agent | Reacts 🙋 when it has asked someone something | Waiting on a person | 

Person | 👍 or 👎 on the agent's reply | Feedback, saved as run.feedback.v1 | 

Person | ✋ on the agent's reply | Stop | 

Person | Replies in the thread | Continues the session; no mention needed | 

A short acknowledgement or a simple yes is a reaction, not a message. The same reactions work on GitHub comments, which carry 👍, 👎, 👀 and 🚀.

Native references

Slack: <@U…> mentions, <#C…> channel links and message permalinks that unfurl. Never a pasted copy of a message that a link would show.

GitHub: #123, @login, commit SHAs and permalinks with line ranges, which GitHub renders as code.

Across surfaces: a Slack reply about a PR links the PR and its exact lines; a GitHub review links back to the session.

A platform prompt, in layers

Every agent should share a basic understanding of how humagen works and one way of behaving. Today only two layers exist: each agent's own prompt, and project instructions (from project templates). Add layers above them, composed in a fixed order:

Layer | Owned by | Holds | Set in | 

Platform | humagen, shipped and versioned | What a session is, mentions, people, alerts, the session tools, reactions, the house style | Built in; overridable by a spec field, as every humagen setting is | 

Workspace | Admins | The company: who we are, our words, our policies, our tone | Settings › Workspace, the spec, or by asking the builder | 

Project | Project owners | Repos, conventions, what "done" means | Project instructions (exists today) | 

Agent | The agent's maintainer | Its job | The agent's prompt | 

Pinned per run. A run records the version of each layer it used, as it already pins the agent's definition, so a retry sees exactly the same prompt.

Visible. The context preview, which already lists what an agent was sent, shows each layer and its size.

Bounded and cached. The shared layers have a size limit and come first, so they form a stable prefix the provider's prompt cache reuses across every agent.

Tested before it applies. Changing the platform or workspace layer runs a sample of every agent's evals and shows the result on the change card, like any agent change.

The platform layer, in part:
You are an agent in humagen. You work in a session: one conversation with you,
started wherever a person is (Slack, GitHub, the console), answered there.
@agent starts or continues that agent's session; @person asks a person.
Use the session tools to delegate, wait, read up and cite other sessions.
Raise an alert only when a person must act.

Lead with the answer. No preamble, no restating the question, no sign-off.
Match the place: in Slack, one to four sentences and no headings;
in a GitHub review, the structured format; in the console, whatever fits.
Ask one question at a time, and only when you cannot proceed.
Link to things instead of quoting them. React instead of acknowledging.
If you have nothing new to say, say nothing.

An online eval enforces it: a Slack reply over its word budget (for example 120 words, unless asked for detail) or opening with filler counts against the agent's health, so drift shows up without anyone reading transcripts.

6. Builder and evals

New agent opens a session with humagen-builder. The same session is where the agent is changed, tested, paused and retired. Each change arrives as a card (prompt diff, tools, where it listens, eval results) for a person to approve. Pause All and Build With the Builder stop being separate buttons.

 | Online evals | Offline evals | 

When | As each run ends | On a schedule, and before a change is saved | 

Against | That run's output and signals (cost, time, tool failures, format, evidence linked) | Suite cases plus recorded traces; a new version replays past inputs | 

Result | Agent health; an alert in the agent's builder session when a limit is crossed | A score per version on the change card; a drop needs an override | 

Cases come from real sessions: every thumbs down with a reason becomes a candidate case. Checks stay deterministic unless a suite marks one as judged by a model, which is labelled wherever it appears. The builder gets tools for pause, retire, connections, writing suites and running them.

7. Connections

Today there are 12 names for one idea (connections, connected accounts, tool servers, MCP servers, clients, systems, installations, apps, sources, providers, connectors, credential references) across five addresses plus Library. None of Notion, Linear or Granola can be connected: Notion loops on a credential reference, and Add Tool Server rejects every host without saying which are allowed. Slack and GitHub accept fake credentials and show "Enabled".

One page, one word: Connections. Presets for Slack, GitHub, Notion, Linear, Granola, Google Drive and BigQuery, plus "Other tool server".

Connect runs OAuth: discovery (RFC 9728, RFC 8414), Dynamic Client Registration (RFC 7591) with PKCE, a pre-registered client where DCR is missing, refresh before expiry, tokens encrypted at rest.

Each connection has one detail page: status and Reconnect, where agents reply (Slack channels, repos), the tools it gives and to which agents, what it syncs for knowledge, the projects using it, and workspace or just me.

Credentials are checked when saved, or the card says "not verified".

An empty state always offers the first action. No page tells a person to edit a config field.

Alerts live on sessions; there is no inbox

Today attention is spread over Notifications (four views, 13 kinds), Home's "Needs you" and "What's new", a project Inbox tab, the phone's Work tab, alert rules and announcements, with counts that disagree. Replace all of it with one object: an alert on a session. The context stays where the work is, and the fix is a reply away.

Part | Rule | 

Where it lives | Every alert belongs to a session, optionally anchored to a message. A system alert (a connection expired, a budget reached, an eval dropped) opens or joins a session with the agent that owns the problem, so "why?" can be asked in place | 

Priority | Urgent, Normal, Low. One word each, one mark each | 

State | Open, Snoozed until a time, Resolved. Alerts are resolved, not read; reading is a property of the session (its unread dot) | 

Who creates it | An agent asking a question or approval (resolves when answered); a failed run; a rule; or a person in plain words: "alert me if the nightly fails", "remind me Friday to check this" | 

How it shows | Open alerts pin to the top of their session with their action (Answer, Approve, Retry, Reconnect), Resolve and Snooze. The session row rises to the top of the list with its priority mark | 

Alert center | One page of open alerts across sessions, Urgent first, filtered by mine or everyone's, priority and source; bulk Resolve and Snooze with Undo. A Watching tab lists standing alerts (rules) and lets you pause or delete them | 

Notifying | Delivery is a preference per priority: Urgent pushes now (Slack DM, email, browser); Normal joins a digest; Low stays in the center. The sidebar badge counts open Urgent and Normal alerts for you, and nothing else | 

Today | Becomes | 

approval, clarification, mention | A Normal alert on that session; resolves when answered | 

failure, budget, alert, source, operation | An alert from a rule, in the session of the agent that owns the problem; Urgent or Normal by rule | 

result, artifact, memory | The session's unread dot; no alert | 

announcement | A session with the people it is for; an alert only if its author flags one | 

Alert rules | Standing alerts in the center's Watching tab, also created by asking | 

Agents get one more tool, alert_create (session, priority, title, who, resolve-when), with alert_resolve, under the same default-deny policy. The API: POST /sessions/{id}/alerts, GET /alerts?state=open&priority=, PATCH /alerts/{id} to resolve or snooze.

Home

Home is the composer and nothing that must be cleaned up. Layout after the reference: a one-line greeting, the composer, one row of text controls under it (project, agent, model and effort, approvals), then at most three rows:

If you have open Urgent or Normal alerts: up to three of them, each with its priority mark, title, session and × to resolve (Undo in a toast), and an Alert center link.

Otherwise: Continue, your three most recent sessions.

Starter suggestions only in a workspace with no sessions yet.

"Needs you", "What's new" and the coloured starter dots go. Sessions that schedules or other agents started nest under their parent or their agent, so a fan-out of twenty runs is one row in your list, not twenty.

Session view

Header: agent, title, project, people, Share, ⋯ (rename, archive, delete).

Open alerts pin above the transcript with their action, Resolve and Snooze.

One Details panel with tabs Files, Sources, Steps and Sessions (children and links), replacing Overview, Workspace, Context and Activity.

Under an answer: Copy, Reply, thumbs up, thumbs down. Fork, Replay and Save go in ⋯; Bring Back merges into Fork.

Feedback: saves on click; only the icon changes, in a neutral selected state; a centred modal adds reason chips for both directions and a comment.

Failures name the cause ("Anthropic key missing", "Budget reached") with Retry where it can work and a working Report Issue.

Composer

One placeholder, short enough for a narrow column: "Message @agent".

Layout follows the composer's own width (container queries), not the window's, so a narrow pane gets the compact layout.

The approval control reads "Approvals: Default", and its menu fits its box.

One project picker. In a session that has answered, it is shown locked with the reason.

The @ menu shows who will answer before sending, offers Continue or Start fresh for an agent already in the session, and says "No agent named @billing" for an unknown name.

A starter fills an empty draft or is added to an existing one, never replacing it.

Stop and Queued are visible states in the composer while an agent works.

/ appears only when there are skills.

Rows, hover and focus

Hand testing found six different row treatments: radii of 0, 7.6, 9.6 and 12.8px, highlight boxes that cut into avatars, four browser tooltips per agent row repeating visible text, and focus rings offset by −2, 0 or 1px. One row component replaces them: a fixed inset, one radius, no title tooltips, one focus ring. At rest a row shows its title, state and age; hover adds only ⋯.

Colour

Flat neutral surfaces. One interaction accent taken from the brand (today "Workspace" and "Red" are the same hue, and red badges read as errors). The moving sweep means working, and appears in the composer, the page's top edge and the sidebar's activity pill; the sidebar's wave and preview stay as they are. Agent colours appear only in agent marks, never as selected states.

Words

One word per idea, from the person's side: session, agent, person, connection, project, alert. No raw ids (personal-7e52…, r250b…), no config keys (credential_scope, person_tools), no permission strings in place of sentences.
